# Static sites

`site/`, `site-inbox/` and `site-developers/` are served as plain files. There is no build step for
the first two and no application server for any of them: `site-developers/` is generated by
`build.py`, and CI keeps the generated output in step with the builder.

| Directory in this repo | Host | Served from | Public name |
| --- | --- | --- | --- |
| `site/` | raijin (wodomini proxies TLS) | `/var/www/pigeonpost` | `pigeonpost.dev` |
| `site-inbox/` | raijin (wodomini proxies TLS) | `/var/www/pigeonpost-inbox` | `inbox.pigeonpost.dev` |
| `site-developers/` | raijin (wodomini proxies TLS) | `/var/www/pigeonpost-developers` | `developers.pigeonpost.dev` |
| `site-enterprise/` | raijin (wodomini proxies TLS) | `/var/www/pigeonpost-enterprise` | `enterprise.pigeonpost.dev` |

Server blocks recorded here: `enterprise.conf` and `developers.conf` (whose CSP allows
`script-src 'self'` for `/docs.js` since Phase 5).

All roots are owned by `www-data`; installation requires the authorized operator's sudo access on
**raijin**. The public TLS proxy remains on wodomini. Do not deploy to its obsolete static copy.
The active webapps master uses `/etc/nginx-raijin-webapps/nginx.conf`; do not restart an unrelated
system or container nginx master.

## Deploying

Build `site-developers/` with `python3 site-developers/build.py` before comparing its output. For
all sites, stage **tracked public assets from a fixed commit** and record SHA-256 hashes. Exclude
tests, node_modules, package manifests, declarations, builders and repository documentation. The
live operator `config.js` and unrelated/untracked assets require an explicit comparison; do not
replace them with defaults or blindly use `rsync --delete`.

Take root-only backups under `/var/backups/pigeonpost/<release>/`, outside every web root, and save
which destination files existed. Install scripts/styles and versioned crypto resources before HTML,
using atomic file replacement. Retain the live database and post-deployment messages during a
rollback; a static rollout does not restore a database. Verify origin and public responses, their
hashes, MIME/security headers and the real browser flow before considering the deployment done.

### Group crypto cache compatibility

The public edge/browser may cache JavaScript for four hours. Replacing an unversioned WASM or
manifest beneath a cached loader breaks integrity checks. Preserve the live unversioned vendor
files for existing clients. Install the complete candidate runtime in
`vendor/groupcrypto/bundles/<WASM_SHA256>/` first: loader.js, integrity.js, pigeonpost_groupcrypto.js
and pigeonpost_groupcrypto_bg.wasm. Treat an installed digest directory as immutable: every file
must match the candidate manifest before reuse; fail on a mismatch.

Include `groupcrypto-map.conf` once inside `http {}` and `groupcrypto-location.conf` in the inbox
server **before other regex locations**. The [map directive](https://nginx.org/en/docs/http/ngx_http_map_module.html)
selects only a full lowercase digest; [try_files](https://nginx.org/en/docs/http/ngx_http_core_module.html#try_files)
resolves that installed bundle under the vhost root. The observed legacy `v=20261020-p3a` alias also keeps its old bundle. Other unknown or malformed versions return404,
without falling back to another bundle. Existing security headers and MIME types are inherited.
Fresh static installations can keep the current bundle in both the default and versioned paths.

Before publishing HTML, run `nginx -t` against the candidate configuration and verify both the
legacy and candidate module hashes through an isolated loopback server. After the exact live
master reload, verify both versions through the public edge. It must preserve the query in its cache
key; a mismatched response blocks HTML publication. The HTML group entry key is the SHA-256 of its
final groups.js bytes, so a UI-only change also invalidates that module; its crypto imports remain
coupled to the WASM digest. Confirm actual same-origin WASM initialization in the shared browser.

## Edge security headers

Content-Security-Policy, `X-Content-Type-Options` and `Referrer-Policy` come from each site's raijin
server block (shared webapps nginx: edit only Pigeonpost blocks, line-addressed, back up and `diff`
before `nginx -t` and reload). Two headers belong at the TLS edge instead, because only the edge
knows the connection was HTTPS and who the client was:

- **wodomini**, each Pigeonpost file in `/etc/nginx/sites-enabled/pigeonpost-*.conf` (these files
  hold only Pigeonpost blocks), inside the `listen 443 ssl` server:
  `add_header Strict-Transport-Security "max-age=31536000" always;` (no `includeSubDomains` or
  `preload`: not every name under pigeonpost.dev is ours to promise HTTPS for). The tunnel block
  also gets `add_header X-Content-Type-Options "nosniff" always;`. None of these files uses
  `add_header` inside a location, so the server-level header reaches every response; keep it so.
- **wodomini**, every proxied location of those servers:
  `proxy_set_header CF-Connecting-IP $remote_addr;`. After `conf.d/cloudflare-real-ip.conf`,
  `$remote_addr` is the visitor for Cloudflare traffic and the real peer for anything else, so a
  client that reaches wodomini without Cloudflare cannot choose the address raijin (which trusts
  `CF-Connecting-IP` from wodomini) and the calls service, billing bridge and broker rate-limit by.
- **postbox host** (45.132.181.100), `/etc/nginx/sites-enabled/pigeonpost-postbox`, TLS server:
  `server_tokens off;`, `add_header Strict-Transport-Security "max-age=31536000" always;` and
  `add_header X-Content-Type-Options "nosniff" always;`.

After any nginx or site deployment run `python3 deploy/sites/check-security-headers.py`; it fails
on a missing HSTS, `nosniff`, CSP directive or referrer policy.

## Checking

```bash
for h in pigeonpost.dev inbox.pigeonpost.dev developers.pigeonpost.dev; do
  printf '%s: ' "$h"; curl -s -o /dev/null -w '%{http_code}\n' "https://$h/"
done
```

Nothing here is versioned with the CLI release. These are static files served at whatever commit was
last pushed to the box, so `git log` on the box is not the answer — compare hashes:

```bash
shasum -a256 site-inbox/app.js
ssh raijin 'shasum -a256 /var/www/pigeonpost-inbox/app.js'
```

## Desktop downloads

The homepage has one platform-neutral Download link. `site/download.html` serves `/download`,
recommends the app for the visitor's OS, and lists all mobile and desktop platforms below.
iPhone and iPad use the App Store, Android uses Google Play, and Windows uses Microsoft Store.
The Mac package is universal for Apple silicon and Intel; Linux offers its released packages.
CLI binaries must never be presented as desktop installers. Platform actions include text labels.

The script reads each platform's description and action from its HTML card, keeping package URLs
in one place. Unknown devices and visitors without JavaScript get manual choices. iPads in desktop
mode still get the App Store recommendation. ChromeOS and unidentified mobile platforms get the
web inbox; the web inbox also remains available beside native app links. It does not infer a Mac's
chip from an `Intel` browser user agent. Update a platform card only after its real installer passes validation.
Versioned GitHub release links keep archives independent of static-site deployment and safe from
static-site deployment.

As verified on 2026-10-21, the live download files are on **raijin** at `/var/www/pigeonpost`, behind
the wodomini proxy; its old static copy is not the current origin. For a downloads-only update,
compare live hashes, back up the affected files outside the web root, and deploy only those files
(JavaScript before HTML). Recheck current routing before using the historical whole-site commands above.

The direct download must use **Developer ID Application** signing, hardened runtime, both
`arm64` and `x86_64`, and an Apple notarization ticket. App Store signing and ad-hoc signatures
do not satisfy the website distribution requirement. Use `.github/workflows/mac-notarize.yml`
on a draft release, then download its final, stapled ZIP and validate it on a Mac. Archive it with
`CODE_SIGN_ENTITLEMENTS=PigeonpostMac/PigeonpostMac-DeveloperID.entitlements`: the default file
claims Sign in with Apple, which only the Mac App Store profile can grant, and a Developer ID app
claiming it is killed at launch (the verifier rejects it):

```bash
python3 deploy/sites/verify-mac-download.py /path/to/Pigeonpost-Desktop-1.0-30.zip \
  --version 1.0 --build 30 \
  --sha256 551898e7ddf71bbe0afa383a274601251ff6af7e8fa64462fd2840ff15ab7db3
```

For a new build, use its approved final SHA-256 and matching version/build number. The verifier
checks the checksum before extraction, both architectures' Developer ID identities and hardened
runtime, absence of the debugger entitlement, the stapled ticket, and Gatekeeper acceptance.
Keep the `SHA256SUMS` release asset in step with the exact ZIP. Publish the separate
`macos-<version>-<build>` release with `--latest=false` so it cannot replace the CLI's latest
`v*` release. Update every archive/release/checksum link and the version, size and minimum macOS
text in `download.html`. Re-download the public asset and rerun the verifier before handoff.

The general site's `script-src 'none'` must stay in place. Install `download-location.conf` as
`/etc/nginx/snippets/pigeonpost-download.conf` and include it **inside the pigeonpost.dev TLS
server**, using `include /etc/nginx/snippets/pigeonpost-download.conf;`. Back up the active
configuration first; run `nginx -t` before reloading. The include permits the page's same-origin
script only on `/download`, `/download/`, and `/download.html`, and keeps its page uncached.
Deploy `download.html`, `download.css`, `download.js`, `brand.css`, `logo_white.png`, and the
updated `index.html`/`account.html` from the same checkout. Copy the new assets before the HTML.
The white logo is the unmodified `assets/img/logo_white.png`, selected by a native `<picture>`
media source in dark themes. No script is needed for the logo or basic download links.

After deployment, verify `/download` and `//download` return the new page, `/download.js` has the
expected contents, and the page's CSP permits `script-src 'self'`. Confirm `/` still has
`script-src 'none'`, `/account` still responds, and the public ZIP matches its approved SHA-256.
To roll back, restore the backed-up site files, active Nginx configuration and prior snippet (or
remove the new include), validate the configuration again, then reload Nginx.

### Linux desktop releases

The native Linux client lives in `apps/linux`; its build plan and progress ledger are tracked there.
Release `linux-desktop-1.0.0` contains x86_64 and ARM64 Flatpak bundles plus an architecture-independent
Debian package. The Actions workflow verifies native GTK, the installed sandbox, Secret Service and
document-portal access, then publishes checksums and GitHub build attestations. Keep its release
separate from the CLI's latest release.

The downloads page selects ARM64 from an explicit Linux platform or supported browser architecture
hints, with the x86_64 Flatpak as the default and every package listed below. Debian/Ubuntu installation
uses `apt install ./<package>.deb` to resolve system dependencies. Flatpak bundles require the GNOME
runtime and manual installation of subsequent releases; do not describe them as a Flathub listing or
automatic update channel. Only update links after public assets and their checksums are verified.

The 2026-09-13 Linux website rollout backed up `download.html`, `download.css` and `download.js` in
`/var/backups/pigeonpost/linux-downloads-20260913`. Existing homepage routing and CSP remain in place.

## enterprise.pigeonpost.dev

`site-enterprise/` (Phase 4, SDS §5) is served by raijin's nginx and reached through wodomini's TLS
proxy, like the inbox since the 2026-10-15 migration. The server blocks are in
`deploy/sites/enterprise.conf`: the files, `/api/` proxied to the billing bridge on 127.0.0.1:8787,
clean URLs, `/app/*` → `app.html`, and `/checkout`, the only page whose CSP admits iyzico.

Keycloak (`pigeonpost-prod`, client `pigeonpost-web`) must list the redirect URI
`https://enterprise.pigeonpost.dev/auth/callback`, the post-logout redirect
`https://enterprise.pigeonpost.dev/`, and the web origin `https://enterprise.pigeonpost.dev`.
The postbox must admit the origin in CORS; the bridge already does.

Deploy the same staging-directory way as the inbox (wodo's home, then one `sudo -S`):

```bash
ts="$(date -u +%Y%m%dT%H%M%SZ)"
rsync -a --delete --exclude node_modules --exclude test --exclude package.json \
  --exclude package-lock.json --exclude README.md site-enterprise/ raijin:pp-enterprise-stage/
printf '%s\n' "$PW" | ssh raijin "sudo -S -p '' sh -c '
  mkdir -p /var/backups/pigeonpost/enterprise-$ts
  [ ! -d /var/www/pigeonpost-enterprise ] || cp -a /var/www/pigeonpost-enterprise /var/backups/pigeonpost/enterprise-$ts/site
  mkdir -p /var/www/pigeonpost-enterprise
  rsync -a --delete ~wodo/pp-enterprise-stage/ /var/www/pigeonpost-enterprise/
  chown -R www-data:www-data /var/www/pigeonpost-enterprise'"
```

Check: `curl -sI https://enterprise.pigeonpost.dev/` returns 200 with the strict CSP, `/checkout`
returns the iyzico CSP with a nonce, and `/api/healthz` answers from the bridge. Before DNS exists,
test through raijin directly: `curl -s -H 'Host: enterprise.pigeonpost.dev' http://192.168.12.165:48880/`.
