## Pairing and authentication boundary foundation

- Added bounded ASCII code and exact-origin fragment-link parsing, typed existing/new-agent previews, safe confirmation/text/identifier bounds and expiry checks. Missing grants and unknown capabilities cannot approve. Codes, target details and confirmations are omitted from diagnostic descriptions. Organization membership and human authorization remain server decisions.
- Added code-only resolve/approve/deny requests on the accepted-login HTTP client. Responses are bounded to 1 MiB; approval acknowledgments must match the reviewed handle and canonical mailbox. Denial returns only an acknowledgment and requires a fresh resolve before a final status can be shown. Network failures never automatically resend these POST decisions.
- The common HTTP path now recognizes a strong-authentication refusal before ordinary token renewal, and again after an ordinary renewal. A malformed strong challenge still stops replay without inventing a method or invalidating the current login. Ordinary expired credentials retain their existing single-renewal behavior. Error bodies are bounded to 64 KiB. Quoted header descriptions cannot inject authentication parameters; duplicates, controls and out-of-range methods/recency are refused. Trusted issuers/redirects cannot be changed by challenge data.

## Scoped approval decisions

- Added an approval store scoped to the human subject and accepted grant, independently of inbox selection. Reads carry revocable child leases; context, operation and reviewed-proof identities guard every result and decision. Expiry, refreshed details, absent/unsupported permissions, account changes and closed views invalidate old confirmations. Network failures hold an unconfirmed result for status inspection.
- Strong sign-in is an explicit separate operation. Only its returned current new grant for the same subject can bridge old-root retirement. Success rereads the request and requires a fresh human approval; it never replays the earlier decision. A different/unreturned grant or a closed view cannot carry the request forward. Denial acknowledgments are followed by a status read, including the concurrent-approval outcome.
- Retained bounded `Retry-After` metadata and account-scoped backoff through code changes and closing/reopening. A different account gets no previous person's request metadata or backoff. Confirmed membership denial forgets private details; session-expiry notification names only its bound grant.
- **All 354 JVM tests pass**, with app compilation and debug lint (`android-enterprise-approval-store-first-core.log`): 17 new controlled state cases and one HTTP rate-limit case. They exercise explicit-only decisions, stale proofs/contexts, expiry/permission refusal, response loss/status inspection, denial races, verified-root transition with no automatic approval, unsupported MFA, wrong-account/unreturned verification, noncancellable results after close, backoff, old reads versus new loading, revocation and double submit. The local rate-limit test draft was invalid and was rejected.

## Scoped room state

- Bound catalog, directory, preview, mutations and openings to the human subject, accepted grant, canonical inbox and selected organization. Independent revocable child requests prevent old completions from replacing new results or clearing new loading state. Old contexts/proofs cannot inspect, decide, clear a replacement preview or navigate to a cached conversation. Revocation clears private metadata.
- Joining and invitation acceptance are separate explicit actions; both require a fresh group read confirming the organization and explicit active/keying membership before opening. Unknown or absent membership cannot open. Read-only organizations permit existing joined rooms, with creation/joining disabled. An uncertain decision requires another preview.
- Creation retains the exact body/key in the live store, refuses changed details and duplicate submission, and requires explicit abandonment before closing an uncertain attempt. A known created ID is checked with a read instead of another creation POST. A confirmed creation remains available to reopen if MLS preparation fails. Account backoff survives mailbox changes and explicit discard. Process-persistent room-creation custody remains a hardening check before native publication.
