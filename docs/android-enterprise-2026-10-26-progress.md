## Pairing and authentication boundary foundation

- Added bounded ASCII code and exact-origin fragment-link parsing, typed existing/new-agent previews, safe confirmation/text/identifier bounds and expiry checks. Missing grants and unknown capabilities cannot approve. Codes, target details and confirmations are omitted from diagnostic descriptions. Organization membership and human authorization remain server decisions.
- Added code-only resolve/approve/deny requests on the accepted-login HTTP client. Responses are bounded to 1 MiB; approval acknowledgments must match the reviewed handle and canonical mailbox. Denial returns only an acknowledgment and requires a fresh resolve before a final status can be shown. Network failures never automatically resend these POST decisions.
- The common HTTP path now recognizes a strong-authentication refusal before ordinary token renewal, and again after an ordinary renewal. A malformed strong challenge still stops replay without inventing a method or invalidating the current login. Ordinary expired credentials retain their existing single-renewal behavior. Error bodies are bounded to 64 KiB. Quoted header descriptions cannot inject authentication parameters; duplicates, controls and out-of-range methods/recency are refused. Trusted issuers/redirects cannot be changed by challenge data.
- **27 new model/actual-HTTP cases and all 327 JVM cases pass**, with app compilation and debug lint (`android-enterprise-pairing-first-core.log`). Coverage includes Unicode lookalikes, typed/absent permission, clock/confirmation bounds, exact renewal bytes, first/repeated/malformed MFA challenges, target substitution, redirects, response bounds, inactive scopes and a late approved response after login replacement.
- All real loopback calendar, direct-message and MLS-group regressions pass after the common transport change (`android-enterprise-pairing-{calendar,direct,group}-regression.log`). No real pairing, agent, room, invitation or media operation is created. Local model drafts reversed security assertions or omitted wire fields and were rejected.
- New leaf sources and tests have parsed Docdex AST records; Kotlin impact graphs have no edges. Exact callers and the compile/runtime/transport checks supplement the graph. Session strong authentication and the native approval/room entry points remain next; this foundation enables no approval screen. Stores remain held.

## Fresh sign-in proof

- Added a pure validator for candidates returned by the fixed token endpoint. It binds both tokens to the existing subject and issuer, the ID nonce/audience, the bearer authorized party, the requested authentication method/recency, issuance and expiry, and an optional exact access-token hash. Malformed candidates produce fixed errors without token/subject text. This checks the app's trusted exchange result; it is not an API for verifying uploaded JWT signatures. The postbox still verifies its bearer and live authority.
- **Nine new proof cases and all 336 core cases pass**, with app compilation (`android-enterprise-strong-proof-first-core.log`). Includes account/issuer/audience/nonce substitution, stale/future clocks, zero-age reauthentication, weak bearer authentication, exact hash binding, algorithm/size/claim refusal and redacted errors. Session integration is not enabled yet.
- Docdex library discovery and library-inclusive search did not provide the nested Gradle AppAuth dependency. Checked the pinned [0.11.1 request builder](https://github.com/openid/AppAuth-Android/blob/0.11.1/library/java/net/openid/appauth/AuthorizationRequest.java) and [connection builder](https://github.com/openid/AppAuth-Android/blob/0.11.1/library/java/net/openid/appauth/connectivity/DefaultConnectionBuilder.java): nonce/PKCE defaults are available and token connections require HTTPS with redirects disabled. Keep those production defaults; use a test-owned connection builder only for native qualification.

## Actual Session verification

- Added explicit strong sign-in using the expected accepted grant, trusted cached AppAuth configuration, normal PKCE/nonce defaults and the bounded authentication requirements. A private waiter returns only the newly accepted grant. The current login and terms remain on cancellation or a rejected candidate; successful same-person verification rotates the grant and preserves current terms. Approval remains a separate future user action.
- Cancellation and adoption meet at one atomic commit point. A stale finalizer only clears its own request. A process-restored strong request is discarded because no live approval waiter exists; an ordinary saved sign-in retains its existing behavior. Unknown/late OAuth callbacks leave replacement pending requests intact, and failure cleanup rechecks generation under the mutex.
- **All 14 targeted native Session cases pass** (ten new strong-flow cases and four existing policy cases), with **336 core tests and debug lint** (`android-enterprise-strong-session-first-runtime.log`). The new cases use the real Session, encrypted storage and SDK token parser through an in-memory connection builder. They cover request parameters/PKCE, same-person adoption/terms/restore, account substitution, weak/stale/nonce-mismatched results, cancellation, abandoned process flows, stale grants, late callbacks, delayed old exchanges, browser-launch failure and ordinary pending restoration. No browser opens and no public authorization/token request occurs.
- No approval entry point or organization room screen is enabled yet. Next: make mailbox/call binding follow completed store activation, then add the scoped approval store and native screens. Existing real-device MFA/media and batch-release gates remain.
