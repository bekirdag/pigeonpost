## Strong sign-in transition

- The Session method receives the exact expected accepted grant and an explicit callback that launches the existing AppAuth activity. It owns a private attempt and deferred result; only a matching, validated completion may return the newly accepted grant. Preserve ordinary sign-in and expiry behavior.
- Use the already trusted configuration, PKCE, the SDK's nonce, `prompt=login` and bounded `acr_values`/`max_age`. Challenges cannot select endpoints. Validate same subject in ID/access tokens, the ID nonce/audience, authorized party, required authentication level and recency, issuance/expiry and any access-token hash before retiring the previous grant. Preserve that person's current terms acceptance only after verified same-person authentication.
- Keep the current accepted session on cancellation or a rejected candidate. Clear old pending requests when starting another flow; generation changes, sign-out and cancellation finish only their own waiter. Finalizers compare attempt identity before touching a pending request. No decision is replayed by a token refresh or a successful sign-in.
- Persist only a marker distinguishing a pending strong flow from ordinary sign-in. A restored process has no live approval waiter and must discard that strong pending flow, retain its protected existing session and require verification again. It must never reinterpret the callback as ordinary sign-in. Pairing codes remain in view memory.
- The approval store's verification job deliberately spans the old-grant retirement. It may adopt only the exact new grant returned by this verified method for the same subject, then perform a fresh read and require another explicit approval. Generic account/store resets must not accidentally adopt a replacement account or erase this specific transition; all other context changes clear the request.
- Include authorization identity in mailbox/group/calendar/call binding decisions or qualify an equivalent deterministic rebind. A state-flow collector must not rely on observing a brief signed-out/empty-mailbox state between two logins for the same inbox.
- Exercise the real Session and AppAuth token parsing with an injected in-memory HTTP connection builder in instrumentation tests. Keep the default production SDK connection builder, trusted endpoints and HTTPS/redirect policy. No browser, public token request, real pairing or credentials are needed for those tests.
