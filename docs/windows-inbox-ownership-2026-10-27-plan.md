# Windows inbox ownership

Continue the [native round-two plan](windows-round2-2026-10-26-plan.md) in an isolated child of media source `0efe3d8`. Keep the media checkout unchanged while #120 qualifies its native build, UI and calls. This work completes the main inbox/draft boundary before message actions, calendar and enterprise screens use it.

1. Expose the accepted login through the inbox/attachment/settings service contracts, preserving context-free stand-ins. Bind the live postbox explicitly to its existing accepted grant; local leases grant no server permission. Inspect symbols and impact paths before editing, and preserve the existing real-MLS baseline.
2. Give each initialized inbox model one account actor. Ordinary token renewal and mailbox switches keep the accepted login; successful reauthentication retires the old actor even for the same canonical inbox. Initialization retains its request intent, rechecks after awaits and clears old private collections, drafts, pending sends, attachments and selections when the accepted login changes. An old action must wait for explicit reinitialization rather than adopt new credentials.
3. Bind every service operation and queued UI continuation to its original account, mailbox and applicable selection. Freeze the account through local file reads, uploads, sends, acknowledgements, contact/privacy changes and notification replies. Retain caller constraints. Confirmed local results may update their original mailbox under the same accepted account; publishing into another selection still requires its mailbox/context generation.
4. Track draft revisions, including attachment changes, so a late send cannot clear a replacement draft merely because its text happens to match. Preserve file drafts on pre-send failures and distinguish uncertain delivery; add no automatic non-idempotent replay. Durable request custody and the message-reference protocol remain explicit subsequent work.
5. Prove the boundary with noncooperative services and held UI continuations: same-mailbox reauthentication, late initialization/load/send, token changes between file stages or acknowledgement calls, old notification actions and replaced draft revisions. Preserve existing cancellation, background refresh, contact grants, thread/notification behavior and all real encryption tests. Run appropriate Core/build/interop checks, then qualify native CI before merging.
