# Pigeonpost v0.2.0 migration and rollback

Status: required operator procedure for every v0.1.0 deployment. This note does not authorize a
production rollout; the legal, witness, custody, identity-provider, and proxy prerequisites in
`docs/law.md`, `docs/runtime-configuration.md`, and `deploy/README.md` remain fail-closed gates.

## What changes on disk

The first v0.2.0 open performs transactional, versioned migrations:

| State | v0.2.0 schema | Important compatibility rule |
| --- | ---: | --- |
| Agent/client SQLite | 15 | The old binary must not open the migrated file |
| Loft SQLite | 6 | The old binary must not open the migrated file |
| Directory SQLite | 4 | The exact v0.1.0/schema-3 shape migrates atomically; unknown shapes are refused |
| Registry SQLite | 8 | A nonempty v0.1.0 log requires its matching signed legacy checkpoint |

The public `PPDISC` disclosure-ledger format is unchanged. Its authenticated `PPDSTAT` restart
sidecar is v2 and stores only constant-sized committed-prefix metadata plus one bounded pending
record; runtime indexes are rebuilt by streaming the public log. Pigeonpost 0.1 did not ship the
offline compliance crate, so there is no production v0.1 disclosure state to migrate. Unreleased
v0.2 development sidecars that persisted growing indexes are deliberately rejected: recreate only
non-production fixtures from the current binary, and never delete or synthesize a sidecar for a
nonempty evidentiary ledger.

The offline destruction inventory is PPinv v3. It adds the authenticated terminal-manifest
commitment and monotonic `Verified`/`Degraded` ciphertext-body result recorded before key-copy
destruction. Canonical unreleased v2 inventories decode with no such evidence and are rewritten as
v3 on the next mutation; v1 and malformed/unknown versions remain refused. Pigeonpost 0.1 shipped
no production inventory, so this compatibility path is for rehearsals and pre-release custody
state only. Do not roll an offline operator back after it has written v3; restore its complete
pre-upgrade custody snapshot instead.

The pre-1.0 `/gh/<login>` spelling is historical only. Registry migration preserves those leaf
bytes and source rows so old checkpoints remain auditable, but v0.2.0 does not claim, rotate, or
resolve `/gh`. Re-prove the GitHub identity and claim `/github/<login>` before advertising a handle.

The loft now reports a proof-of-work floor that was not met as HTTP `403 Forbidden`. Proof of work
is a recipient-controlled, non-monetary delivery policy; the historical `402` response was an
incorrect status choice and is not a compatibility contract. Clients must treat the stable
Pigeonpost error code, rather than the old HTTP status, as the protocol result.

Client schema 10 adds `registry_handle_audit`, the compact global replay frontier, and
`registry_handle_projection`, the normalized latest provider-subject/key state for every canonical
handle encountered in that continuous replay. Existing handle cache rows remain available for
offline use, but the first online handle lookup after upgrade rebuilds the projection from leaf zero
before it can advance the sole `registry_pin`; later lookups fetch only appended leaves.

Client schema 11 adds `spam_marks`, a recipient-local idempotency ledger keyed by message id. It
makes repeated or concurrent mark-as-spam actions apply at most one score penalty for each stored
message while keeping allowlist removal, message-state mutation, and score adjustment in one
transaction. Once `user_version` is 11, a v0.1.0 client or an earlier v0.2.0 build must not open or
write that agent database; restore the complete pre-upgrade backup before any binary rollback.

Client schema 12 adds the exact placement journal: one current signed agent record, its per-URL
own-loft/rendezvous completion rows, per-rotation publication targets, and durable directory-refresh
health. Migration does not invent completed work. The next bounded wake derives the deterministic
target set from verified local/directory state, publishes exact persisted bytes, and records each
successful URL independently. A process restart therefore resumes partial record or rotation
publication without allocating a new sequence or repeating already acknowledged targets. Once
`user_version` is 12, restore the complete pre-upgrade backup before rolling back to any schema-11
binary.

Client schema 13 validates every legacy inbox/outbox payload against the new persistence bounds,
erases wraps and capability tokens from already successful or terminal copies, and installs exact
transactional usage counters with finite inbox-message/body and outbox-row/payload limits. A limit
may be raised only within the audited hard maximum and may not be lowered below current usage.
Successful or terminal copies retain bounded payload-free delivery metadata; an undelivered copy is
never removed automatically. Migration raises a default only as far as required to admit existing
schema-12 data and otherwise rolls back untouched. Once `user_version` is 13, restore the complete
pre-upgrade backup before rolling back to schema 12 or earlier.

Client schema 14 first validates every handle-projection row against the witnessed audit frontier,
then installs the public-key index used by recipient reputation, authenticated per-loft retention,
and permanent received-message deletion tombstones. Deletion erases body, sender, timestamp,
attribution, and spam-mark state but retains the message id indefinitely to prevent replay. Those
tombstones have a separate one-million-entry hard ceiling, consume no active inbox quota, and are
never automatically evicted. A removed loft is drained for `min(authenticated advertised
retention, 30 days)`; retired key material still follows its separately signed 90-day window, but
can use only routes that remain active or within that bounded removal window. Once `user_version` is
14, restore the complete pre-upgrade backup before rolling back to schema 13 or earlier.

Client schema 15 adds the nullable fixed-length canonical attribution requirement to signed
resolution-cache rows and separate exact sender/recipient requirement settings. The 34-byte codec
binds version, jurisdiction, and stable authority; write and cached-resolution read paths reject
unknown versions or jurisdictions, all-zero authorities, wrong lengths, and trailing bytes. Legacy
`attribution_required=true` and jurisdiction-only sender settings remain stored only so access can
fail closed and require an explicit exact reconfiguration—migration never invents an authority.
The v14→v15 DDL runs in one transaction after exact predecessor-shape and invariant validation; any
failure leaves `user_version` and the schema at 14. Once `user_version` is 15, restore the complete
pre-upgrade backup before rolling back to schema 14 or earlier.

Loft schema 5 charges policy, agent-record, and rotation control rows exactly and reserves the
bounded future rotation row at agent-record acceptance. Schema 6 adds the durable, UTC-minute-aligned
global trace-admission singleton. A trace-enabled service charges that counter before sink mutation,
does not refund a later failure, and refuses backward time or a store without durable admission.
Fresh schema-6 databases begin with an empty counter; upgrading an existing predecessor
conservatively consumes the current minute so a restart cannot grant a second admission window.
The durable value is a reservation high-water: each FULL-synchronous refill reserves at most 64
slots, unused slots burn on restart/rollover/limit change, and every local dispense rechecks the
singleton. Both migrations reconcile exact table/index/constraint shape and accounting before
readiness.

Registry schema 7 adds the durable global verified-binding admission singleton. Provider claims
charge it after identity verification but before claim-trace submission or log append; its exact
ceiling is the smaller of the configured HTTP request ceiling and the canonical maximum of 454,795
bindings per minute at 10,000 records per segment. Shorter segments lower that realizable ceiling.
Restart,
concurrent processes, and later failure cannot create or refund admissions. Every supported existing
predecessor—including an authenticated unversioned v0.1.0 import and the v6→v7 migration—consumes
its rollout minute, while a genuinely fresh schema-7 database begins empty. Refills reserve at most
64 slots under FULL synchronization; unused reserve burns and can only rate-limit early. Provider
serving also requires a purpose-separated trace-capacity contract covering the same exact global
rate, segment size, complete jurisdiction/capture/retention policy, every configured UTC-key epoch,
and both logical purpose-store caps. The witnessed public path accepts only the audited built-in
sealed claim-trace adapter; custom sinks remain usable only in the explicit loopback test fixture
and cannot self-assert production readiness. Witnessed serving also requires the Registry to retain
an owner-custodied persistent database; in-memory, temporary, and SQLite URI spellings are
test/development-only and fail the public gate.

Registry schema 8 makes identity challenge consumption and handle append one atomic transaction.
Each consumed challenge records the exact committed binding sequence, so a client retry after a
dropped server timeout recovers the same leaf instead of burning authorization or appending twice.
The v7→v8 migration invalidates outstanding ephemeral challenges; operators must restart any OAuth
or OIDC flow begun before the upgrade.

Directory schema 4 adds the bounded exact-mutation reservation table used by add/drain
pre-admission. A reservation is committed with WAL `synchronous=FULL` before the directory signs or
sends its immutable registry leaf; witnessed finalization consumes it atomically with the local
projection and checkpoint. Startup recovery exact-replays any reservation left by cancellation,
ambiguous registry response, or process failure, and readiness remains false until recovery
completes. The immediate schema-3 predecessor is shape-verified before DDL, so a partial or modified
schema-3 database remains at version 3 and requires operator review. The verifier compares
canonical `sqlite_schema` table and explicit-index SQL with schemas generated from both the
pristine and exact v0.1.0 lineages; matching column names cannot hide altered types, nullability,
defaults, primary/unique keys, `CHECK` constraints, or missing/changed indexes. The same verification
runs on schema 4 before it is accepted. Production `directory serve` also requires the retained
owner-custodied persistent database opened through this path and revalidates its named file and
private parent before listener startup and during public readiness; in-memory state is test-only
and cannot pass that gate.

Every migration refuses a future schema and rolls back the migration transaction on malformed or
unknown state. That is not a substitute for a restorable pre-upgrade backup.

## Rehearse before touching a host

Run the checked-in drill from the exact release source and repeat the black-box scenarios with the
downloaded, checksum- and attestation-verified binary:

```bash
./deploy/acceptance/migration-rollback.sh
PIGEONPOST_BIN="$PWD/pigeonpost-linux-x64" \
  ./deploy/acceptance/local.sh --binary-only
```

The drill uses the exact v0.1.0 SQL fixtures, includes a WAL-backed sentinel, restores through
SQLite's backup API, compares logical dumps, and executes every forward-migration/refusal test.

## Pre-upgrade checkpoint

Perform these steps separately on each host and keep the backup outside the live volume:

1. Record the running image digest or binary SHA-256, service configuration SHA-256 values, public
   checkpoint, directory signing-key fingerprint, and current health/readiness results.
2. Stop every Pigeonpost writer. Confirm the registry, directory, and loft processes are gone before
   opening any database with the candidate binary.
3. Run `PRAGMA quick_check`, record `PRAGMA user_version`, and take a WAL-aware backup with SQLite's
   backup API or a stopped-volume snapshot that includes the database, WAL, SHM, configuration,
   signing-key, registry-audit, trace, and outbox files.
4. Restore the backup into a separate scratch location, run `PRAGMA integrity_check`, and compare a
   logical dump or storage-snapshot manifest with the stopped source. Record backup checksums.
5. For a nonempty legacy registry, save the last operator-signed checkpoint to an owner-only file.
   Verify its origin, size, and root before passing it through `--legacy-checkpoint`; never invent or
   regenerate this authorization.
6. Before opening the directory database, verify that it is a regular, current-user-owned,
   single-link `0600`-or-stricter file in a current-user-owned private directory. The v0.2.0 runtime
   refuses unsafe existing files instead of changing their permissions. Windows deployments must
   provide the equivalent protected current-user DACL, non-reparse, single-link, stable-file-ID,
   and safe-parent guarantees. Remediate custody only while the service is stopped and only after
   the restorable backup above has been verified.
7. Record the existing signed directory document's public signing key and place that exact key in
   `registry.toml` as `server.directory_publisher_keys` before starting the upgraded registry. For a
   new directory, provision the owner-only `signing_key_file` first and derive the public pin from
   that seed. Never copy the directory seed onto the registry host.

Do not rotate, replace, or regenerate `checkpoint.key` during the upgrade. Its continuity is part of
the public log identity.

## Upgrade order

Use the immutable v0.2.0 digest or verified native binary for every step.

1. **Registry:** start it alone with the directory publisher pin already configured, supplying the
   legacy checkpoint when required. Require `/health`,
   then require `/v1/log/status` to report a fresh witnessed published head with acceptable lag.
   Compare the public dump and checkpoint continuity with the pre-upgrade record. Stop immediately
   on any migration, origin, key, witness, or log-root error.
2. **Directory:** start it against that witnessed registry. Require `/health`, `/ready`, a valid
   signed `directory.json`, and continuity of the directory signing key before proceeding.
3. **Loft:** start it only after its witnessed compliance-key cache, trace policy, proxy-source
   evidence, and current purpose/jurisdiction keys are ready. Require `/health` and `/ready` and
   confirm that `/v1/info` advertises the exact configured canonical origin and expected loft key,
   then confirm capacity/retention.
4. **Clients:** allow each isolated agent home to migrate on first v0.2.0 open. Preserve each home
   independently; never point two readers at one agent state. Flush queued copies and run a
   Pigeonpost send/fetch/read exchange without retaining plaintext in logs.

Move to the next role only after the current role is healthy and protocol-ready. A liveness response
alone is not sufficient.

## Rollback

An old binary must never open a forward-migrated database.

1. Stop all v0.2.0 writers.
2. Preserve the failed upgraded state separately for investigation; do not overwrite the only copy.
3. Restore the complete, verified pre-upgrade database/config/key/trace/outbox snapshot, including
   the registry checkpoint key and any WAL state captured by the backup mechanism.
4. Re-select the previously recorded immutable image digest or binary checksum.
5. Start registry, directory, and loft in the same order as above and repeat continuity/readiness
   checks. Restore client homes before starting the prior client binary.

If the pre-upgrade restore cannot be verified, keep services stopped. Reusing the previous image
against v0.2.0 state is not a rollback and can destroy the evidence needed for recovery.
