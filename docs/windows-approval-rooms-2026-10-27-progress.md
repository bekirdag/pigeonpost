## Approval store, native confirmation and verified rebind

- `Enterprise/DeviceApprovalStore.cs` ports the qualified Android contract. It binds to the signed-in person (hashed owner hint) and the exact accepted grant, runs every request inside a revocable child of that grant, and keeps the code and confirmation in memory only. Each decision names the currently reviewed screen (context and proof); a replaced account, a changed screen or expiry refuses it. Denial is acknowledgment only and is followed by a fresh resolve; a lost approval or denial reply becomes *unconfirmed* and is never resent; only an explicit status check and another human action can follow. `429` honours a bounded `Retry-After` (new `PostboxException.RetryAfter`).
- A strong-authentication refusal shows a verification step instead of retrying. `VerifySignIn` runs outside the old actor, accepts only a different live grant of the same person, rebinds, rereads the same code and waits for another explicit approval. Another person, the same grant, a failure or cancellation never resolves or approves.
- `Enterprise/StrongSignInBroker.cs` composes the PR136 pieces: request-owned `127.0.0.1` loopback return, `AccountSession.BeginStrongSignIn`, the system browser, and same-person adoption. A browser that cannot open, a returned denial or cancellation leaves the existing sign-in untouched.
- Rebind after verified adoption: `InboxViewModel.CarryUnsentWork(prior)` keeps text and file drafts and selections (including typing during the browser step) and restores them only into a different live grant of the same person, dropping drafts for inboxes the new grant does not list. `GroupsModel.CarryUnsentWork(prior)` returns an unsent group draft only when that same group is reopened after the fresh membership read. Verification is refused during calls, sends, edits/replies and group sends. The desktop then restarts the normal account path (inbox, events, calls, calendar, groups) under the new grant; machine approval stays on screen because it is account-scoped.
- Native page (`MainWindow.Approval.cs`): organization, prominent handle, explicit new-agent vs existing-agent (canonical inbox) wording, machine label, requested access, the network hint labelled as not proof, a live expiry countdown and a large monospaced confirmation number. Approval needs a 1.5 s pointer hold or, for keyboard and Narrator, *Approve with confirmation…* with a confirmation dialog whose default is Cancel. Status uses live regions. Entry is the *Approve a machine* navigation item when the server lists `orgs`.
