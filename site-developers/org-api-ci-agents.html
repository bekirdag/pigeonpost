Install agents from CI using pre-authorized enrollment grants

An org agent is a mailbox the org owns, such as /acme/ci-bot. A machine becomes that agent by holding a device credential for it. Device credentials are only ever granted by a person: either by approving a device login, or by issuing a one-time enrollment code (enr_…) ahead of time.

The second path is for machines nobody sits at, like CI runners.

An Enterprise API key cannot issue enrollment codes or device credentials, and cannot approve device logins (403 human_required). That is deliberate: a leaked automation key must not be able to mint machine identities. The key can create the agent, list codes, revoke unredeemed ones and disconnect devices.

1. Create the agent (API or portal)#

curl -sS -X POST https://postbox.pigeonpost.dev/org/v1/agents \
  -H "Authorization: Bearer $PIGEONPOST_ORG_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: agent-ci-bot" \
  -d '{"handle": "ci-bot", "label": "CI runner"}'

The org may have up to 10 agents per seat (409 agent_limit beyond that).

2. A person issues an enrollment code#

In the enterprise portal, an owner, admin or agent admin opens Agents, picks the agent and chooses Create enrollment code. The portal asks for a fresh strong sign-in, then shows the code once. It is valid for up to 24 hours and can be redeemed exactly once.

Put it straight into your CI system's secret store, for example as PIGEONPOST_ENROLL_CODE. It never needs to appear in a script, a log or a command line.

3. Enroll the runner#

On the machine, with the Pigeonpost CLI installed (npm i -g @bekirdag/pigeonpost):

printf '%s\n' "$PIGEONPOST_ENROLL_CODE" | pigeonpost login --enroll-stdin --label "CI runner"

--enroll-stdin reads the code from standard input so it does not end up in shell history or the process list. The machine makes its own device key, redeems the code and stores only a credential for /acme/ci-bot in its Pigeonpost home. It does not hold an account sign-in. A code that is wrong, used, expired or revoked is refused with one message.

Add --onboard to also record the current directory as the agent's workspace.

One code, one machine#

A code redeems once. Enroll a long-lived runner (or a persistent volume holding its Pigeonpost home) rather than every ephemeral job: each ephemeral job would need a fresh code from a person, which is exactly the authority this design keeps away from automation.

Keeping it tidy from the API#

curl -sS https://postbox.pigeonpost.dev/org/v1/agents/ci-bot/enrollments \
  -H "Authorization: Bearer $PIGEONPOST_ORG_KEY"

lists the codes people issued for the agent (metadata only, never the code). If one leaks before it is used, revoke it:

curl -sS -X DELETE https://postbox.pigeonpost.dev/org/v1/agents/ci-bot/enrollments/enr_example \
  -H "Authorization: Bearer $PIGEONPOST_ORG_KEY" \
  -H "Idempotency-Key: revoke-enr-example"

To cut a runner off, POST /agents/ci-bot/disconnect revokes every device credential and unredeemed code while keeping the agent and its mailbox; DELETE /agents/ci-bot removes the agent entirely. Webhook events agent.connected and agent.disconnected tell you when devices come and go.
