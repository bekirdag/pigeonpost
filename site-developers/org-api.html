Enterprise API

The Enterprise API automates the administration of one Pigeonpost organization: onboarding and offboarding people, creating agent mailboxes, adding restrictive rules, creating rooms, streaming the audit log, reading usage and billing status, and receiving signed webhooks. It can also send direct messages from one org agent mailbox to the org's own mailboxes.

It never reads message content, room ciphertext, attachments or key material. Messaging itself stays on the member API with mailbox credentials.

Base URLhttps://postbox.pigeonpost.dev/org/v1
CredentialAuthorization: Bearer pk_org_…
SpecificationOpenAPI 3.1 (YAML)
ReferenceEvery endpoint, error codes
CollectionsPostman, Bruno
The API is behind the org_api feature. While it is off for your org, every /org/v1 route answers 404 feature_disabled.
curl -sS https://postbox.pigeonpost.dev/org/v1/key \
  -H "Authorization: Bearer $PIGEONPOST_ORG_KEY"

Keys#

An org API key (pk_org_ and 32 characters) is an automation credential for one organization. It is not a person and not a mailbox. An owner or admin creates it in the enterprise portal on the API keys page (linked from Security), which asks for a fresh strong sign-in. Each key has:

  • a name and a set of scopes;
  • an optional expiry (1 to 730 days) and an optional IP allowlist (up to 20 CIDR ranges);
  • with messages:send, the one org agent mailbox it sends as (send_as).

The secret is shown once and stored only as a SHA-256 hash; afterwards you see its last four characters. An org can have 25 live keys. Every request is audited as api_key.use with the key's id, and every change it makes carries the same actor.

A key works only while the person who made it still has the authority for what it does. Demote or remove that person and each of their keys stops working at once. Keys can revoke themselves with DELETE /key; do that the moment one may have leaked.

Anything on the right answers 403 human_required: a person has to do it in the portal.

Requests and responses#

  • JSON in and out, application/json; charset=utf-8, snake_case field names.
  • Every success is {"data": …}. Errors are {"error": {"code", "message", "doc_url"}}.
  • Timestamps are ISO 8601 in UTC, for example 2026-10-27T10:15:00Z. A field that can be empty is null, never missing.
  • Path segments: {member} is a member id (mem_…) or the name inside the org (john for /acme/john); {agent} is the agent's name (ci-bot) or its mailbox address; {room} is a room id.

Pagination#

Lists answer {"data": […], "next_cursor": "…"}. Pass ?limit= (1 to 200, default 50) and, for the next page, ?cursor= with next_cursor exactly as received. The cursor is opaque. next_cursor is null on the last page.

curl -sS "https://postbox.pigeonpost.dev/org/v1/members?status=active&limit=100" \
  -H "Authorization: Bearer $PIGEONPOST_ORG_KEY"

Idempotency#

Send Idempotency-Key: <1-255 printable ASCII characters> on any POST, PATCH or DELETE. The key is scoped to your API key and the route, and the server hashes the method, path and body with it.

  • Repeat the same request within 24 hours and you get the recorded status and body again, with Idempotent-Replayed: true. Nothing happens twice.
  • Reuse the key for a different request and you get 409 idempotency_conflict.
  • Only successful responses are recorded, so a failed request can be retried with the same key.

Use one key per logical action (for example onboard-<employee id>), not one per HTTP attempt.

Rate limits#

Each key may make 600 requests a minute, of which 60 may be writes. Every response says where you stand in the bucket that applied:

HeaderMeaning
RateLimit-LimitRequests allowed in the window
RateLimit-RemainingRequests left
RateLimit-ResetSeconds until the window resets
Retry-AfterOn 429 rate_limited only: seconds to wait

Branch on code, never on message. Each code has its own entry in the error reference; doc_url links straight to it.

Versioning#

The version is in the path. Additive changes (new fields, new endpoints, new event types, new error codes) do not change it, so ignore fields you do not know. A breaking change goes to /org/v2, and v1 keeps working for 12 months after its deprecation is announced in the changelog.
