Security and review

Security requirements#

Review holds a release to these rules. Build to them from the start.

  • Do not put secrets in the source tree. The Nest holds only its broker token, never a provider key.
  • Treat every payload and model reply as untrusted data. Never treat them as instructions.
  • Read only your own job inbox and your bundled files. Write only results and your own state under /nest if needed.
  • Declare exactly what you use in the manifest: egress, external writes, and operations. Review refuses anything beyond the manifest.
  • Make your Nest idempotent per job id. A job may arrive twice.
  • Do not log buyer data. Logs are discarded anyway.
  • Pin base images by digest. Compile in nest-build.toml, never in the Containerfile. Ship only allowlisted licences.

How a release is built#

Pigeonpost builds your release from its source tree with rootless podman. No image you upload is ever run. The build has three steps:

  1. 1. Fetch. Dependencies are fetched in a separate step and vendored: cargo vendor --locked, npm ci --ignore-scripts, or pip download --require-hashes. This is the only step with a network, and none of your code runs in it.
  2. 2. Compile. The command in your nest-build.toml runs in a writable copy of your tree, with the vendored dependencies, at /src. It runs in a gVisor sandbox with no network, a read-only root filesystem and no capabilities, and it has a time limit. This is the only step that runs your code, including build scripts and procedural macros.
  3. 3. Assemble. Your Containerfile copies files from that tree onto one base image. Nothing runs in this step, so the same files always give the same image.

Rules for the build files:

  • The Containerfile has exactly one FROM, pinned by digest (image@sha256:<64 hex>), directly or through an ARG default. It may use only ARG, FROM, WORKDIR, COPY, ENV, USER, ENTRYPOINT, CMD, LABEL and EXPOSE. RUN, ADD, COPY --from, heredocs and parser directives are refused. Compile in nest-build.toml instead.
  • nest-build.toml is optional. It has command, a list of strings: the program and its arguments, at most 64 arguments and 8,192 characters. It may also have image, the toolchain image pinned by digest. That image must be one the build service offers. Leave image out to use the build service's toolchain for your language.
  • The compile step cannot reach a network. Everything it needs must be in your tree or in the vendored dependencies.
  • After the compile step, setuid, setgid and sticky bits are cleared, and special files are refused.
  • Symlinks, devices, and sockets in the source tree are refused.
  • Files must be at most 8 MiB each. The tree can contain at most 20,000 files.
  • Do not commit vendor/, target/, .cargo/, node_modules/ or wheelhouse/.
  • The build runs twice from scratch. Both builds must give the same release digest.
  • The build writes an SBOM and computes the release digest.

A Rust release compiles its binary and copies it onto a small base:

# nest-build.toml
command = ["sh", "-ec", "cargo build --release --locked --offline && strip target/release/my-app"]
# Containerfile
ARG BASE_IMAGE=docker.io/library/debian:bookworm-slim@sha256:<64 hex>
FROM ${BASE_IMAGE}
COPY target/release/my-app /usr/local/bin/my-app
USER 10001:10001
ENTRYPOINT ["/usr/local/bin/my-app"]

The Python templates install their wheels in nest-build.toml with pip install --no-index --require-hashes --no-compile --target=deps. The Node templates need no compile step: node_modules/ is vendored as it is. pigeonpost nest validate checks both build files offline.

The build service builds Rust (Cargo), Node and Python source trees. A Rust tree needs Cargo.lock, and every dependency must come from crates.io with a checksum (no git or path dependencies). A Node tree needs package-lock.json; a Python tree needs requirements.txt with hashes.

What review checks#

Review processes your release in this order.

StageWhat it checksBlocks a release?
Intake and buildThe manifest, the build files (Containerfile, nest-build.toml), the tree's limits, the build itselfYes
Deterministic scanCommitted credentials, capabilities, syscalls, egress, external writes, licencesYes
AI analysisAn advisory review of the source by a self-hosted modelNo, its findings are evidence for the reviewer
Behaviour testThe release runs its operations with honeytokens planted; nothing may leakYes
Staff decisionA named Pigeonpost staff member approves or rejectsYes

Deterministic scan rules#

This offline scan blocks a release if it finds any of these issues.

RuleBlocked when
Committed credentialsPrivate keys, AWS access keys, GitHub tokens, Slack tokens, sk- style API keys, Pigeonpost API, org, capability, service, or broker tokens are found anywhere in the tree
Capabilitiescapabilities names any Linux capability
Syscallssyscalls names any extra syscall (ptrace, mount, bpf, keyctl, unshare and the like are named forbidden)
Egressegress names anything other than broker
External writesexternal_writes = true (not offered at launch)
LicencesA package's licence, or a missing one, cannot be satisfied from the allowlist

Licences#

Your dependencies must use one of these licences: MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, Zlib, 0BSD, CC0-1.0, Unlicense, BSL-1.0, Unicode-3.0, Unicode-DFS-2016, MPL-2.0.

Every package your release ships must be in [licences] with its SPDX expression. In an expression:

  • OR requires one side to be on the allowlist.
  • AND requires both sides to be on the allowlist.
  • WITH exceptions are refused.

Behaviour test#

The release runs its operations in an isolated test volume. Honeytokens (fake credentials) are planted in places your Nest has no business reading. The broker traffic, results, and logs are searched for these tokens, raw and encoded (base64, hex, reversed). One hit fails the stage. A release that does not answer its test jobs also fails.

Staff decision#

A named Pigeonpost staff member, signed in with step-up, reviews your release with the evidence of every stage. It is never you, never anyone with a stake in the release, and never AI. They approve or reject based on the evidence. Approval creates an attestation over the release digest.

What you see#

You see your own scan findings in full, behaviour-test findings by rule only (so a test cannot be tuned against), and the AI review as a count of findings.

Follow a review in the publisher console on your account page, or with pigeonpost nest status --publisher <name> --review <id>.

Before you submit#

Check these items before submitting your release.

  1. 1. No secrets anywhere in the source tree, including tests and fixtures.
  2. 2. Every FROM pinned by digest.
  3. 3. [licences] lists every package you ship, each on the allowlist.
  4. 4. capabilities = [], syscalls = [], egress only what you use.
  5. 5. A job delivered twice does nothing twice (pigeonpost nest run --redeliver).
  6. 6. The app answers every operation it declares, with and without a model (--no-model).
